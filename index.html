Chartwise: AI Clinical Documentation Pipeline

A clinician uploads a visit transcript. Chartwise pulls the patient's history from a FHIR server, has an LLM draft a SOAP note, safety-checks the draft, and queues it for review. The approved note is saved back to the patient's record, and every view, edit, and approval is audited. All patient data is synthetic, generated with Synthea.

click a stage to see how it handles failure

What it does

The Spring Boot encounter service stores the encounter (transcript AES-256-GCM encrypted) and an outbox event in one database transaction, then returns 202 Accepted. A relay publishes the outbox to Kafka.

When things break

The two rows commit or roll back together, so an encounter can never exist without being processed. Intake only writes two rows, so during a simulated LLM outage uploads were still accepted at full rate.

What it does

Carries encounter.created, note.drafted and note.approved, keyed by encounter ID. Events carry IDs only: the transcript stays behind an audited API and never enters Kafka.

When things break

Messages that keep failing go to a dead-letter topic and become a visible DRAFT_FAILED state an admin can retry, instead of silently disappearing.

What it does

Fetches the visit's draft context (no name or identifiers), drafts several notes concurrently, validates the SOAP structure, and publishes note.drafted.

When things break

Offsets are committed only after Kafka acknowledges the draft, and only up to the first unfinished message per partition. Killing the worker mid-stream across 200 encounters left 0 lost and 0 duplicated notes.

What it does

The only path to the LLM: Redis token-bucket rate limiting, retries with jittered backoff, and a circuit breaker in front of the Claude API, served over gRPC.

When things break

The gateway fails fast while the worker waits patiently. In a simulated 60-second provider outage the breaker opened in 8s, the backlog peaked at 153 and drained after recovery, and 0 drafts failed.

What it does

Flags medications in the draft that appear in neither the patient's record nor the transcript, and drugs started despite a recorded allergy (penicillin allergy → amoxicillin).

What it catches

Caught 100% of 500 injected errors with 0 false positives on 400 clean drafts. The limits are measured too: injected drugs come from its own drug list, and doses aren't checked.

What it does

Shows the transcript and draft side by side. Every save is a new version, with a diff against the original AI draft.

Guardrails

Only clinicians can approve, and only the version they are looking at. Every view, edit, and approval goes to an append-only audit log, enforced by a Postgres trigger.

What it does

The approved note is written to the patient's record on a HAPI FHIR server as a DocumentReference, and the encounter becomes FILED.

When things break

A FHIR write can't join a database transaction, so filing does an idempotent conditional create keyed by encounter ID first, then marks the encounter filed. A retry can't file the note twice.

  • Used a transactional outbox and idempotent Kafka consumers so no encounter is lost or processed twice; killing the worker mid-stream across 200 encounters left 0 lost and 0 duplicated notes

  • Wrote a medication safety check that caught 100% of 500 injected drug and allergy errors (drawn from its own drug list) with 0 false positives on 400 clean drafts; encrypted PHI at rest and made the audit log append-only

batchserve: Dynamic Batching Inference Server

Go Concurrency
  • Built a request-batching inference server in Go (standard library only) that amortizes a fixed per-call backend cost across batched requests, raising goodput 12.8× (23 → 299 req/s) and eliminating timeouts at 300 req/s
  • Implemented bounded-queue admission control, deadline dropping of abandoned work, and size-or-time flushing, mapping each outcome to a distinct status so callers separate “never attempted” (503) from “backend failed” (500)
  • Showed queue depth dictates failure mode: a 1024-slot queue timed out 3,271 requests at 23 req/s, while a 16-slot queue shed load in microseconds and held 125 req/s at stable p99, 5.4× more useful work
  • Validated with a 44-test suite under Go's race detector, adding a regression test reproducing a metrics data race the existing concurrency test could not surface
